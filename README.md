# ModularBlazor.Module.Elsa

Elsa: the optional Elsa workflow engine, for newsroom automation. It is a module of the [ModularBlazor](https://github.com/soft-square-net/ModularBlazor.Platform) platform, released on its own as the bundle `elsa`.

> **Status: moved in.** The code moved here from the platform repo and builds against the platform packages.
> Nothing here is packed as a bundle yet: build it and upload the entry project's output in the admin area.

## Layout

```
src/WebApi.Modules.Elsa.Infrastructure/   entry assembly: IRuntimeModule, Elsa wiring
playground/   Aspire AppHost for local development, and two checks (check.ps1, check-newsroom.ps1)
tests/        unit tests, and integration tests that run newsroom workflows on a real PostgreSQL
module.json   bundle manifest, generated by the pack step
```

## Building

```bash
dotnet build
dotnet test
```

The integration tests start a PostgreSQL container, so `dotnet test` needs Docker.

The platform packages come from the soft-square-net GitHub Packages feed, which needs a token to restore even though
the packages are public: create a personal access token (classic) with `read:packages` and put it in the environment
as `GITHUB_PACKAGES_TOKEN` (`NuGet.Config` reads it). The platform version is pinned once, in `global.json`.

Tools that need the platform's source run from a checkout of
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform), pointed at this repo:
`src/WebApi/scripts/Export-ModuleOpenApi.ps1 -Project <this repo>/src/<entry project> -ModuleId <id>` re-exports the
OpenAPI document, and `src/WebApi/scripts/Add-Migration.ps1 -Project <this repo>/src/<entry project> -Name <Name>`
adds a migration for every database provider.

## How it builds and ships

- It compiles against the platform's contract packages (`WebApi.Contracts`, `ModularBlazor.Abstractions`, ...) from the
  soft-square-net GitHub Packages feed. It never references platform source.
- CI packs one bundle per release: `<module>-<version>.modpkg`, a zip with `module.json`, `server/`, `client/` and
  `contracts/`. The platform's admin area installs it: server part first (tenant migrations), then the client part.
- One version for the whole bundle, set once from the git tag. Unchanged parts are skipped on install.
- An API client ships once, inside the bundle that owns the API, as a hidden client module. Modules that call it
  reference its package with `ExcludeAssets="runtime"` and declare a dependency with a version range in `module.json`.

## Developing

`playground/` is a small Aspire AppHost: PostgreSQL, RabbitMQ, the platform's identity service, gateway and Blazor
client, a `core` pool with Organization, Shifts, DynamicFields and Content, and a `workflow` pool with this repo's
module. Both pools load modules straight from their build output, so there is nothing to pack or upload: change code,
rebuild, restart the pool. It is not part of the solution, and CI does not build or run it.

It needs Docker, a ModularBlazor.Platform checkout at the version in `global.json`, and built checkouts of the four
modules (`dotnet build` in each, Debug). By default all of them sit next to this repo, as `Platform` and
`Module.Organization`, `Module.Shifts`, `Module.DynamicFields` and `Module.Content`. `Module.NewsRoom` is optional: when
it is there and built, the `core` pool loads it too; when it is not, the playground starts without it and says so.

```powershell
dotnet run --project playground
```

Other places: add `-p:PlatformRoot=<path>/` (with the trailing slash) for the platform, and
`-- --Playground:SiblingsRoot=<path>` for the modules (or `--Playground:Content=<path>` for one of them).

It uses the platform lab's ports (client 5070, gateway 5080, identity 5090, pools 5081 and 5082), so stop the lab and
any other playground first. Data stays in the Docker volume `elsa-playground-data` and in `playground/.data/`.

- **Tenants** `acme` and `globex`, each with an administrator who holds every workflow permission:
  `acme-admin@modular.local` (password in the platform's identity `appsettings.Development.json`) and
  `globex-admin@modular.local` (added by `AppHost.cs`).
- **Service client** `elsa-workflows`. Its secret is the app host's `Parameters:elsa-client-secret` user secret
  (`dotnet user-secrets set Parameters:elsa-client-secret <value> --project playground`), else a development-only
  value. Never put a real secret in the repo. The identity service has one configurable service client, so here
  Organization and Shifts sign in with it too; a real deployment gives each its own.
- **Grants.** The `seed-grants` resource (`playground/seed-grants.ps1`, safe to rerun) gives `elsa-workflows`, in each
  tenant, `content.assign`, `content.transfer`, `content.publish`, `content.unit.assign`, `shifts.manage`,
  `newsroom.workflow`, `org.read` and `dynamicfields.read` (why each: [src/README.md](src/README.md#grants)).
- **Elsa's API** through the gateway: `http://localhost:5080/api/elsa/elsa/api/...`.

### The workflow check

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File playground\check.ps1
```

Add `-PlatformRoot <path>` and `-SiblingsRoot <path>` for checkouts elsewhere. It builds and starts the playground,
then checks that a trivial workflow (write, wait for an event, write) runs for `acme` and that `globex` cannot list,
read, run, delete or resume it. It then stops every process and container, starts them again on the same volume, and
checks that the definition and the suspended instance survived, that `globex` still cannot reach them, and that `acme`'s
event finishes the instance. It also checks the calls `elsa-workflows` needs. It exits with 1 if a check fails. With a
playground that is already running, use `-Phase Start`, restart it, then `-Phase Verify`.

### The newsroom check

With the playground running and `Module.NewsRoom` (with its bindings, routing and workload API) built:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File playground\check-newsroom.ps1
```

Add `-PlatformRoot <path>` for a platform checkout elsewhere. It prepares a Section, a press, a category, a post kind, a
shift and a routing rule, and approves a proposal while no workflow is bound: none starts, NewsRoom reports the setup
error and a [dry run](src/README.md#dry-run) says why. It then binds the post kind to `newsroom-post` and checks that
NewsRoom's event starts the [default workflows](src/README.md#default-workflows), and that the real events take the
post from filing, through its content's sub-workflow and one return by the desk, to publication. A second project is
killed to check that its sub-workflow is cancelled too. It plays the writer and the desk itself. It leaves its data
behind (a central organization `elsa-playground` with a seed for `acme`, proposals, posts, shifts) and can be run again.
